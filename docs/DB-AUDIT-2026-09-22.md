# DB 스키마 감사 2026-09-22

대상: 플랫폼 Supabase(`wfcesrpz…`) **라이브 스키마**(PostgREST OpenAPI로 직접 조회) vs 리포 SQL(`supabase/migrations/*.sql`, `RUN-*.sql`). Cloud Supabase(`fsnqxknb…`)는 **DNS 해석 불가**(§3).

## 1. 라이브 플랫폼 스키마 (실제)

| 테이블 | 행 | 컬럼 | 코드 참조 |
|---|---|---|---|
| `generation_usage_v2` | 2 | user_id PK, period_month, month_count, **period_day, day_count**(미사용), **carryover_count**(예약), updated_at | `freeTrial.ts`(클라이언트 RPC), `AccountUsageBlock.tsx`. **서버 라우트는 이 테이블을 읽거나 쓰지 않는다**(`api.chat.ts`는 `message_usage`만) |

## 2. 발견

### 2-1. 리포 ↔ 라이브 드리프트 (기능 영향 있음)
- **`deployed_apps`**: 리포 마이그레이션(`20260825000001`)은 `storage_mode text check(sample|cloud|supabase)` + `storage_expires_at`. 라이브는 옛 `RUN-2-deployed-apps.sql`이 만든 `supabase_connected boolean`. 코드는 `storage_mode`로 insert하다 `42703`이면 두 컬럼을 빼고 재시도하는 **폴백으로 운영 중**(`deployedApps.ts:144,159`) → "저장 기능 켠 앱"의 storage_mode가 DB에 안 남는다. `apps.tsx`가 만료 표시 못 함.
- **적용 안 된 리포 마이그레이션**: `20260825000001`의 storage 컬럼. `RUN-2-metering-v2-fix.sql`(=`0831`)은 RPC 정의만이라 적용 여부를 OpenAPI로는 판별 불가 — `select pg_get_functiondef('public.increment_generation_count_v2'::regproc)`로 확인 필요. **2026-09-22 실측: 라이브 `get_generation_status_v2`가 `{monthLimit:1, canEdit:false, carryover:0}`를 반환 → `feat/access-policy`의 RUN-7 버전이 적용돼 있다(리포 `supabase/migrations/`에는 없음). `main` 코드는 10건 전제.**
- `onboarding_responses`는 `RUN-5`만 있고 `supabase/migrations/`에 없음(라이브에는 존재).

### 2-2. 중복·불필요
- **v1 메터링 3종**(`user_generation_usage`, `get_generation_count()`, `increment_generation_count()`): 코드 참조 0, 리포 SQL 없음. v2가 대체.
- `rls_auto_enable()`: 리포 없음, 참조 없음 — 대시보드에서 만든 유틸 추정.
- `generation_usage_v2.period_day/day_count`: 0831에서 "읽지 않지만 남김". RPC가 계속 써서 죽은 컬럼을 매 호출 갱신.
- `deployed_apps.supabase_connected`: `storage_mode='supabase'`와 동일 의미, 코드 참조 0.
- **SQL 파일 중복**: `RUN-1` = `0825000000`, `RUN-2-metering-v2-fix` = `0831`, `RUN-6` = `0911` (내용 동일). `RUN-2-deployed-apps` ≠ `0825000001`(storage vs supabase_connected — 라이브는 RUN 쪽). → RUN 파일을 `supabase/migrations/manual/`로 이동(이 커밋), "정본은 `supabase/migrations/`" 명시.

### 2-3. 관계·제약 문제
- `deployed_apps(provider, project_name)` 유니크 없음 — `deployed_app_project_owned_by_other` RPC가 전제하는 불변식이 DB에서 강제되지 않음(경쟁 조건 시 중복 가능).
- `message_usage`에 `chat_id`, `(user_id, created_at)`, `model` 인덱스 없음 — 요금제·운영 집계가 풀스캔.
- `generation_usage_v2.updated_at`은 RPC만 세팅 — 운영 중 수동 PATCH(쿼터 리셋)에서 갱신 안 됨 → 트리거.
- `message_usage.user_id on delete set null` + `api.account-delete`가 `auth.admin.deleteUser`만 호출 → 탈퇴 후 익명 원장 행 잔존(의도라면 OK, 개인정보 관점 확인). **Cloud 프로젝트의 `cloud_apps.owner_user_id`는 FK가 아니라 탈퇴해도 앱·문서가 남는다**(R2 미디어, Pages 프로젝트도). 탈퇴 = 플랫폼 auth 행 삭제 이상이 아님.
- `deployed_app_project_owned_by_other` RPC가 `anon`에게 execute 허용(`20260826`) — 서버가 anon 키로 부르기 위해서지만, 결과적으로 anon 키 소지자 누구나 "이 프로젝트명이 남의 것인가"를 조회할 수 있다.
- FK는 전부 `auth.users`로만 향함. 테이블 간 FK 없음(`deployed_apps.chat_id`·`message_usage.chat_id`·`onboarding_responses.chat_id`는 텍스트, 채팅은 클라 IndexedDB라 서버에 `chats` 테이블이 없다 — 앱이 커지면 첫 번째로 필요한 테이블).

### 2-4. 네이밍
- 테이블·컬럼 snake_case 일관 ✓. `_v2` 접미(`generation_usage_v2`, RPC `*_v2`)는 v1 삭제 후 이름만 남는 잔재 — 코드·RPC 이름이 묶여 있어 리네임은 대규모(보류, 다음 메터링 개편 때).
- `onboarding_responses.q1_audience…q5_palette` — 질문 번호가 컬럼명. 질문 순서 바뀌면 의미 깨짐 → 다음 스키마 개편 시 `audience, storage, industry…`로.
- 시각 컬럼 혼재: `deployed_at`, `created_at`, `updated_at` — OK. `period_month text('YYYY-MM')` — date로 바꾸면 인덱스·비교 정확(보류).

## 3. Cloud 프로젝트 — 접속 불가
`CLOUD_SUPABASE_URL=https://fsnqxknbtplygxcyltsg.supabase.co` **DNS 해석 실패**(getaddrinfo 11001). 프로젝트가 일시중지(무료 플랜 7일 비활성) 또는 삭제. 프로덕션 시크릿의 값이 같은지 확인 필요(`wrangler pages secret list`는 이름만 보임). 켜져 있지 않으면 "저장 기능 켜기"(`/api/cloud-provision`)와 배포된 사용자 앱의 저장이 전부 실패한다. **사용자 확인 항목 #1.** 리포 정본은 `manual/RUN-3-cloud.sql` + `RUN-4`(cloud_apps·cloud_documents·cloud_usage·cloud_rate_limit + RPC/트리거 + RLS). RLS는 4테이블 on, 정책은 `cloud_apps_service_role_all` 하나 — 서버가 `CLOUD_SUPABASE_SERVICE_KEY`로만 접근하니 anon/authenticated는 전부 거부(의도). 코드 쪽 격리는 `app_id`+`device_key` 필터(`cloudDocuments.ts`)이고 사용자 단위 격리는 없다(`docs/API.md` Cloud 절).

## 4. 만든 마이그레이션

| 파일 | 성격 | 적용 |
|---|---|---|
| `supabase/migrations/20260922000000_platform_schema_cleanup_safe.sql` | **추가만** — storage 컬럼+check+백필, `(provider, project_name)` 유니크, message_usage 인덱스 3, updated_at 트리거, 테이블 코멘트. 전부 idempotent | 플랫폼 SQL editor에서 실행 → `/api/health` 200 → 배포 후 `deployedApps.ts` 폴백 로그 소멸 확인 |
| `supabase/migrations/20260922000001_platform_schema_cleanup_destructive.sql.pending` | **삭제** — v1 3종, `rls_auto_enable`, `supabase_connected`, `period_day/day_count`(+RPC 재정의) | `.pending` = 자동 대상 아님. **사용자가 스냅샷 확인 후 직접**. 항목별 rollback 주석 |

기존 기능 영향: 1단계는 코드 변경 없이 폴백 경로가 정상 경로로 바뀌는 것뿐. 2단계 D는 RPC 재정의 — 라이브 함수가 0831 버전인지 `pg_get_functiondef`로 먼저 대조.
