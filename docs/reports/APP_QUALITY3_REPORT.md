작업일: 2026-08-29
브랜치: `overnight5`
대상 파일: `app/lib/common/prompts/new-prompt.ts`

지시하신 대로, **새 규칙을 쌓지 않고 기존 문구를 손보는 방식**으로 3건을 고쳤습니다.

## 1) 3건 각각 어떻게 고쳤는지 (전 → 후)

### 실패 1 — 샘플 데이터 내적 일관성 (카페 앱, 대표 지표 -990P)

**전** (`Starting Data`): "샘플 데이터로 시드하라"고만 했지, 항목들끼리 계산이 맞아야
한다거나 대표 숫자가 양수여야 한다는 말은 없었습니다. 그래서 적립(+4, +6)보다 사용
(-1,000)이 더 큰 항목을 아무렇게나 넣어서 대표 지표가 음수가 됐습니다.

**후**: 같은 문장에 이어서 — "**모든 파생 숫자(잔액·합계·포인트)가 항목들로부터 정확히
계산되고, 그 결과가 양수여야 한다 — 항목을 먼저 정하지 말고 자연스러운 양수 대표
숫자를 먼저 정한 뒤 거기서 거꾸로 항목을 구성한다. 대표 지표가 0이거나 음수면 실패다**"를
추가했습니다.

### 실패 2 — 비수치형 앱에 빈약한 차트 삽입 (카페 앱, 2개짜리 막대 차트)

**전**: "최소 3개 지점, 앱 카테고리가 가계부/트래커류면 차트를 넣는다"는 기준 — 그런데
"카페 포인트 적립"도 "logs"(기록)로 느슨하게 분류될 여지가 있었고, 실제로 3개 미만인데도
차트를 넣어 자기 기준조차 어겼습니다.

**후**: 판단 기준을 앱 "카테고리"가 아니라 **데이터 자체의 양**으로 바꿨습니다 — "샘플
데이터에 **같은 종류 값이 5개 이상** 쌓여 있고 추이/비중이 실제로 읽을 가치가 있을 때만"
차트를 넣고, "2-4개의 얕은/무관한/막 생긴 값은 자격이 안 되며 이럴 땐 요약 카드나 리스트로
대체한다, **데이터가 빈약한 억지 차트는 차트가 아예 없는 것보다 못하다**"를 명시했습니다.
기존 "라이브러리 설치 금지", "수치 없는 앱은 완전히 건너뜀" 문구는 그대로 뒀습니다. 이
기준과 맞물리도록 `Starting Data`의 "2-5개 항목" 문구에도 "차트가 5개 이상 같은 종류
값을 필요로 하면 더 넣어도 된다"는 한 구절을 붙였습니다.

### 실패 3 — 데스크톱 밀도 (2회 연속 실패)

원인 추정 및 근거는 2번 항목 참고. 아래 세 군데를 고쳤습니다(새 섹션 추가 없이, 전부
기존 문구 보강/이동):

1. **`<coralred_design_system>`의 `LAYOUT` 줄**(파일 최상단 근처, "CRITICAL" 표시가
   붙은 블록)에 데스크톱 그리드 규칙을 한 문장 추가: "≥1024px에서는 지표 카드와
   리스트+차트 쌍이 `.cr-grid-3`/`.cr-grid-4`/`.cr-grid-2`를 쓴다 — 그 폭에서 `.cr-stack`
   한 줄짜리는 모바일 레이아웃을 그대로 둔 것이지 완성된 데스크톱이 아니다."
2. **`Screen Density`** 절 자체를 그리드 클래스 이름으로 다시 씀 — "3-4열 그리드"
   같은 서술 대신 `.cr-grid-3`/`.cr-grid-4`/`.cr-grid-2`/`.cr-page`를 직접 지목하고,
   "이 클래스들은 LAYOUT에서 이미 정의된 바로 그것"이라고 명시.
3. **`<mobile_first_web>`**(별도의, design_instructions보다 뒤에 오는 독립 블록)의
   "Single-column layouts by default" 문장을 "1024px 미만은 단일 열, 그 이상은
   Screen Density의 그리드 규칙을 따른다 — 모바일 우선은 데스크톱도 모바일과 같은
   레이아웃으로 끝난다는 뜻이 아니다"로 명시적으로 갈라놨고, "375px에서 확인" 문장에
   "1200px에서도" 확인하라는 말을 더했습니다(모바일에만 있던 구체적 검증 지시를
   데스크톱에도 똑같이 부여).
4. 자가 점검 문구도 "위 패턴"이라는 막연한 표현 대신 `.cr-grid-*`/`.cr-page`를 직접
   지목하도록 다듬었습니다.

## 2) 실패 3의 원인 추정과 근거

파일을 구조적으로 살펴본 결과, 세 후보 중 **(a)와 (b)가 실제 원인, (c)는 기각**으로
판단했습니다:

- **(c) 스타터 템플릿 컨테이너가 좁게 고정 — 기각**: 디자인 키트 CSS
  (`design-handoff/coralred-ui.css:170`)를 직접 확인했더니 `.cr-page { max-width: 1120px }`로,
  요청하신 1100-1200px 범위 안에 이미 정확히 들어와 있었습니다. 컨테이너 자체는 문제가
  아니었습니다. 증상("가운데 좁은 열에 몰리고 하단이 비어있다")은 컨테이너가 좁아서가
  아니라, **1120px 컨테이너 안에서 카드들을 그리드가 아니라 세로로 한 줄씩 쌓아서**
  생기는 걸로 보입니다 — 그러면 폭 1120px 안에서도 콘텐츠가 세로로 길게 늘어지고
  좌우/하단에 여백만 남습니다.
- **(a) 지시 위치가 묻힘 — 근거 있음**: 실제로 그리드 클래스(`.cr-grid-{2,3,4}`)가
  정의된 곳은 `<coralred_design_system>`(파일 134번째 줄 근처, "CRITICAL" 표시,
  61줄짜리 비교적 짧은 블록)인데, "언제 3-4열을 써야 하는가"라는 요구사항은
  `<design_instructions>`(625번째 줄 근처, 140줄짜리 블록, 지난 두 라운드에서 계속
  섹션이 늘어난 곳) 안의 `Screen Density`에만 있었습니다. 두 지점 사이에
  `<database_instructions>`(333줄짜리, 파일에서 가장 긴 블록)가 통째로 끼어 있어서,
  "도구(그리드 클래스)"와 "언제 쓰는지"가 프롬프트상 거의 500줄 떨어져 있었습니다.
- **(b) 모바일 우선 지시와 충돌 — 근거 있음**: `<mobile_first_web>`은
  `<design_instructions>` 바로 다음에 오는, 8줄짜리 짧고 독립된 블록입니다. 그 안의
  "Single-column layouts by default"와 "Check the layout at 375px width before
  finalizing"는 데스크톱 조건 없이 단독으로 읽어도 완결된 지시처럼 보이고, 구체적인
  검증 방법(375px에서 직접 확인)까지 딸려 있어서 실행 우선순위가 높습니다. 반면
  데스크톱 요구사항은 `Screen Density`(길고 복잡한 블록 안 여러 항목 중 하나)와
  `Pre-Completion Self-Check`(체크리스트 항목 중 하나)에만 있어서 상대적으로
  존재감이 약했습니다.

**결론**: "그리드를 어떻게 쓰는지"(도구)와 "언제 써야 하는지"(요구사항)가 프롬프트
안에서 물리적으로 멀리 떨어져 있었고, 그 사이에 짧고 강한 모바일 전용 지시가 끼어들어
데스크톱 요구사항의 존재감을 더 약하게 만든 것으로 판단했습니다. 그래서 지시 위치를
새로 만들기보다, **그리드 클래스가 정의된 바로 그 자리(LAYOUT 줄)에 "언제 쓰는지"를
직접 붙이고**, `Screen Density`와 `mobile_first_web`이 서로를 명시적으로
참조하도록(같은 클래스, 같은 규칙이라고) 고쳤습니다.

## 4) 재실측 계획

같은 두 케이스를 다시 생성해서 이번엔 아래를 집중적으로 확인해주세요:

### 케이스 1 — "가계부 앱 만들어줘"
- 대표 지표(잔액/합계)가 양수인가
- 차트가 있다면 같은 종류 값이 5개 이상인가(3개가 아니라)
- 데스크톱에서 지표 카드가 실제로 여러 열로 나열되는가, 하단 공백이 줄었는가

### 케이스 2 — "동네 카페 포인트 적립 앱 만들어줘"
- **차트가 아예 없어야 정상** — 이전처럼 2개짜리 막대가 다시 나오면 이번 수정도
  실패, 다른 방식으로 다시 봐야 함
- 대표 지표(누적 포인트 등)가 양수인가
- 데스크톱 밀도 개선 여부는 동일하게 확인

이번에도 실제 브라우저가 없는 환경이라 **직접 실행은 못 했습니다** — 위는 실행 계획일
뿐입니다. 결과 알려주시면 이어가겠습니다.
