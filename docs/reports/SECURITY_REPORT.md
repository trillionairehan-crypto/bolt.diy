## 1. 뭐가 어떻게 막히게 됐는지 (전/후 비교)

### 대상 API 3개
- `api.cloudflare-deploy.ts` — 앱 배포 실행
- `api.cloudflare-domain.ts` — 커스텀 도메인 연결/상태 조회
- `api.payment.verify.ts` — 결제 조회 (참고: 이 API는 아직 화면 어디에서도 호출하지 않음, 결제 연동 준비용)

### 이전 (수정 전)
누구든 프로젝트 이름이나 결제 ID 문자열만 알면, 로그인 여부와 관계없이 요청을 보낼 수 있었습니다.
- 남의 프로젝트 이름을 추측/유출로 알아내면 그 이름으로 재배포하거나 도메인을 연결할 수 있었음
- 남의 결제 ID를 알면 결제 내역을 조회할 수 있었음

### 이후 (수정 후)

**1) 로그인하지 않은 요청 → 401 차단**
```
요청: POST /api/cloudflare-deploy (Authorization 헤더 없음)
응답: 401 { "error": "로그인이 필요해요." }
```
로그인 화면에서 쓰는 것과 동일한 Supabase 로그인 세션 토큰을 `Authorization: Bearer <토큰>` 헤더로
보내야만 통과합니다. 가짜/만료된 토큰도 동일하게 401로 거부됩니다.

**2) 남의 프로젝트에 대한 배포/도메인 연결 → 403 차단**
```
요청: POST /api/cloudflare-deploy (내 계정 토큰, projectName="다른사람이 이미 쓰는 이름")
응답: 403 { "error": "이 프로젝트는 다른 계정에 연결돼 있어요." }
```
단, 이 검사는 §3에서 설명하듯 새 DB 마이그레이션이 적용되기 전까지는 아직 실제로 동작하지 않습니다
(로그인 검사와 달리, DB 준비가 안 됐을 땐 안전하게 "통과"시키도록 설계했습니다 — 이유는 아래 §4).

**3) 정상적인 내 배포/재배포는 그대로 동작**
```
요청: POST /api/cloudflare-deploy (내 계정 토큰, projectName="내가 만든 프로젝트" 또는 "완전히 새 이름")
응답: 200 (기존과 동일하게 배포 진행)
```

**4) 결제 조회도 로그인 필요**
```
요청: POST /api/payment/verify (Authorization 헤더 없음)
응답: 401 { "verified": false, "error": "login_required" }
```

기존에 화면에 표시되던 에러 알럿(토스트 메시지 등)이 새 401/403 메시지도 그대로 띄워줍니다.
화면 쪽 코드를 따로 바꿀 필요가 없었습니다.

## 2. 프로덕션에 추가해야 할 환경변수

**새로 추가해야 할 환경변수는 없습니다.**

이번 인증 기능은 기존에 이미 있는 플랫폼 로그인용 Supabase 값
(`VITE_PLATFORM_SUPABASE_URL`, `VITE_PLATFORM_SUPABASE_ANON_KEY`)을 그대로 재사용합니다.
이 값들은 이미 프로덕션에 설정되어 있어야 로그인 자체가 동작하므로, 별도 조치가 필요 없습니다.
(값 자체는 이 보고서에 기록하지 않습니다.)

단, 소유권 검사(§1의 2번)를 실제로 동작시키려면 **DB 마이그레이션 적용**이 별도로 필요합니다 — §3 참고.
이건 환경변수가 아니라 DB 작업입니다.

## 3. 브라우저에서 직접 확인할 체크리스트

- [ ] **로그아웃 상태에서 배포 버튼을 눌러본다** → "로그인이 필요해요" 같은 한국어 메시지가 알럿/토스트로 뜨는지 확인
- [ ] **로그인 상태에서 평소처럼 배포**해본다 → 이전과 동일하게 정상 배포되는지 확인 (회귀 없어야 함)
- [ ] **로그인 상태에서 커스텀 도메인 연결**을 시도해본다 → 이전과 동일하게 정상 동작하는지 확인
- [ ] **도메인 연결 상태 조회(폴링)**도 로그인 상태에서 계속 정상적으로 갱신되는지 확인
- [ ] (마이그레이션 적용 후에만 의미 있음) 계정 A로 만든 프로젝트 이름을 계정 B로 로그인해서
      재배포/도메인 연결 시도 → "이 프로젝트는 다른 계정에 연결돼 있어요" 메시지와 함께 거부되는지 확인

**DB 마이그레이션 적용 방법** (소유권 검사를 실제로 켜려면):
1. `supabase/migrations/20260825000001_deployed_apps.sql` — 아직 적용 안 됐다면 먼저 적용
2. `supabase/migrations/20260826000000_deployed_apps_ownership_check.sql` — 이번에 새로 작성한 마이그레이션, 위 파일 다음에 적용

두 파일 다 플랫폼 Supabase 프로젝트의 SQL 편집기에 붙여넣거나 `supabase db push`로 적용하면 됩니다.
적용 전에는 §1의 2번(소유권 차단)만 동작하지 않고, 나머지(로그인 차단)는 이미 정상 동작합니다.

## 4. 일부러 안 한 것과 그 이유

- **결제 "플랜 활성화" 로직은 만들지 않았습니다.** 지시사항대로 `api.payment.verify.ts`에는
  로그인 확인만 추가했습니다. 사용자가 결제 연동 작업을 별도로 진행 중이기 때문입니다.
  다만 나중에 활성화 코드를 만들 때 지켜야 할 설계 메모(같은 결제 ID로 중복 처리되지 않도록
  DB에 UNIQUE 제약을 거는 방식)를 `SECURITY_PLAN.md`에 남겨뒀습니다.

- **소유권 검사는 DB 마이그레이션이 적용되기 전까지는 "통과(허용)"로 동작합니다 (Fail-Open).**
  이유: 이 검사가 기대는 `deployed_apps` 테이블과 새 함수가 아직 실제 DB에 적용돼 있지 않습니다.
  만약 검사 실패 시 "차단"하도록 만들었다면, 마이그레이션을 적용하기 전까지 코드가 배포되는 순간부터
  **모든 사용자의 배포/도메인 연결 기능이 통째로 멈춥니다.** 이건 지시사항의 "기존 기능이 깨지면 안 된다"는
  원칙에 정면으로 위배됩니다. 반면 로그인 확인(§1의 1번)은 항상 "차단" 방향으로 동작합니다 —
  이건 이미 완전히 준비된 기능(로그인 시스템)에 기대는 것이라 예외를 둘 이유가 없기 때문입니다.

- **속도 제한(rate limiting)은 이번 3개 API에 추가하지 않았습니다.** 지시사항에 없었고,
  이번 작업 범위(신원 확인·소유권 확인)를 벗어나는 별도 주제라고 판단했습니다.

- **`app/routes/pricing.tsx`는 열지도, 건드리지도 않았습니다.** 커밋 안 된 사용자 작업이 있다는
  안내에 따라 완전히 손대지 않았습니다 (`git status`로 이번 커밋에서 제외됐음을 확인).

- **테스트는 전부 모킹(가짜 응답)으로 처리했습니다.** 실제 Cloudflare API, 실제 Supabase DB,
  실제 PortOne 결제 서버에는 이번 작업 중 단 한 번도 실제 요청을 보내지 않았습니다.
