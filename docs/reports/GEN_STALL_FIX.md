## 원인

### 확정된 것 — 채팅 주소(chatId)가 세 번 바뀌는 이유
**확정입니다.** 코드에서 실수를 직접 찾았습니다.

새 채팅이 시작되면 `useChatHistory.ts`라는 파일의 `storeMessageHistory`라는 함수가 채팅
주소(URL)를 정하는데, 여기에 변수 이름이 겹치는 실수가 있었습니다. 함수 안에서 "임시
주소"를 계산해서 담아두는 변수와, 그 값을 화면에 반영하는 React 상태 변수의 이름이
똑같아서, 코드의 뒷부분이 방금 계산한 새 값이 아니라 **아직 반영되지 않은 예전 값**을
계속 쳐다보고 있었습니다. 그 결과:
1. 템플릿을 가져온 직후 만들어지는 임시 주소(예: `2-1787932499138-0`)로 한 번 이동
2. 곧바로 실제 채팅 번호(예: `26`)로 다시 이동 — 그런데 이때도 "아직 주소가 없다"는
   낡은 정보를 보고 판단해서 불필요하게 한 번 더 이동이 걸림
3. 다음 순간 다시 임시 주소로 돌아감 — 같은 이유로 또 한 번 낡은 정보를 보고 판단

이게 사용자께서 콘솔에서 보신 "Chat ID changed" 3연속 로그의 정확한 원인입니다. 변수를
헷갈리지 않게 고쳤습니다.

### 아직 완전히 확정은 아닌 것 — "그래서 왜 진짜 생성 요청이 서버에 안 갔는지"
**여기서부터는 강한 정황 증거는 있지만 100% 확정은 아닙니다.** 이 작업 환경에는 실제
브라우저로 재현해볼 방법이 없어서(전에 색상 문제 검증 때와 같은 제약), 실제로 이
채팅-주소 문제가 생성 요청 자체를 막는지, 아니면 그냥 겉보기에만 어지러운 현상이고
진짜 원인은 따로 있는지를 코드만으로 완전히 증명하지는 못했습니다.

확실히 발견한 건, 템플릿을 가져온 다음 실제 생성을 시작시키는 `regenerate()`라는 호출이
**"제대로 됐는지 결과를 확인하지 않고 그냥 쏘고 잊어버리는" 방식**으로 돼 있었다는
점입니다. 이 함수가 내부적으로 실패(예외)해도 그걸 받아서 처리하는 코드가 어디에도
없었습니다 — 즉 지시하신 "예외를 삼키는 지점"이 정확히 여기 있었습니다. 실패해도 아무
에러 메시지도, 로그도 안 남고 그냥 "아무 일도 안 일어난 것처럼" 멈춰버릴 수 있는
구조였습니다. 이 부분이 실제 원인이 아니더라도 고쳐야 하는 결함이라 판단해서 고쳤고,
다음에 또 이 문제가 재현되면 — 이번엔 반드시 콘솔에 흔적이 남게 됩니다.

### 배제한 것 — 최근 커밋(모바일 레이아웃, 워크벤치 뷰 정리) 영향 아님
말씀하신 두 커밋(`cc4b8be` 모바일 레이아웃, `a8fb9b1` 워크벤치 뷰 정리)이 실제로 어떤
파일을 건드렸는지 확인했습니다. 이 문제가 발생하는 코드(`Chat.client.tsx`,
`useChatHistory.ts`)는 두 커밋 어디에도 포함되지 않았습니다 — **두 커밋은 이 문제의
원인이 아닙니다.**

대신, 문제가 된 코드 패턴(템플릿 메시지를 강제로 채워넣고 `regenerate()`를 부르는 방식)
자체는 이보다 훨씬 전인 2026-08-20, AI 응답 처리 라이브러리를 구버전에서 신버전으로
옮기던 작업 때부터 있었던 것으로 확인됐습니다. 그때 남긴 코드 주석에도 "신버전에서 이
방식이 실제로 잘 동작하는지 끝까지 검증되지 않았다"고 이미 적혀 있었습니다 — 이번에
그 우려가 실제로 문제였을 가능성이 있다는 뜻입니다.

## 조치

1. **채팅 주소가 세 번 바뀌는 버그를 고쳤습니다** (`useChatHistory.ts`). 변수 이름이
   겹쳐서 낡은 값을 보던 부분을, 항상 최신 값을 보도록 고쳤습니다. 이제 새 채팅을 만들
   때 주소가 한 번만 정해지고 오락가락하지 않습니다.
2. **생성 요청이 실패해도 조용히 사라지지 않게 고쳤습니다** (`Chat.client.tsx`). 템플릿을
   가져온 직후 실제 생성을 시작시키는 지점 두 곳(템플릿을 성공적으로 가져왔을 때 /
   기본 설정으로 생성할 때) 모두에 "요청을 시작한다"는 기록을 남기고, 요청이 실패하면
   기존에 이미 있던 에러 화면(요청 실패 알림)이 뜨도록 연결했습니다.

**추측만으로 여러 곳을 동시에 고치지 않았습니다.** 확정된 채팅 주소 버그는 근본 원인을
고쳤고, "진짜 멈추는 이유"는 완전히 확정하지 못했기 때문에 그 부분은 "다음에 실패하면
반드시 흔적이 남게"만 만들고 멈췄습니다.

3. **여전히 멈추면:**
   - 브라우저 개발자 도구(F12) → 콘솔 탭에서 `Chat`이라는 이름으로 시작하는 로그를
     확인해주세요. `generateNewApp: template seeded, triggering regenerate()` (또는
     `baseline seeded`) 로그가 보이는지, 그 바로 뒤에 에러 로그
     (`regenerate() rejected...`)가 있는지 확인해주세요.
     - 로그가 아예 안 보이면: `regenerate()` 호출까지도 도달을 못 한 것 — 그 앞
       단계(템플릿 가져오기 자체)에 새로운 문제가 있다는 뜻이라 다시 조사가 필요합니다.
     - "triggering regenerate()"는 보이는데 에러 로그가 없으면: 요청은 정상적으로
       나갔는데 서버 쪽 문제일 가능성이 커집니다 — 이때는 `wrangler tail`로 서버 로그도
       같이 봐주세요.
     - 에러 로그가 보이면: 화면에도 이제 에러 알림이 떠야 합니다 — 그 알림에 적힌 내용을
       알려주시면 바로 다음 원인을 좁힐 수 있습니다.
   - 이 로그들을 캡처해서 알려주시면, 지금 확정하지 못한 부분까지 마저 좁혀서
     고치겠습니다.
