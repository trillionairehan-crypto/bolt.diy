## 작업 1. 저장(코랄레드 Cloud) 만료 정책 — 배포 안 된 앱 7일 / 배포된 앱 30일

### 조사한 것
- 만료 시점은 `cloud_apps` 표의 `expires_at` 칼럼 하나가 전부 결정합니다. 저장 기능을 처음 켤 때
  "지금부터 7일 뒤"로 한 번 정해지고, 그동안은 아무도 이 값을 바꾸지 않았습니다.
- 실제로 정리(삭제)하는 쪽은 `RUN-3-cloud.sql`에 이미 있는 `cloud_expire_cleanup()`이라는
  함수로, 매시간 자동 실행되면서 `expires_at`이 지난 앱의 데이터만 지웁니다. 이 함수 자체는
  손댈 필요가 없었습니다 — `expires_at` 값만 정확하면 알아서 맞게 동작합니다.
- `deployed_apps` 표에도 `storage_expires_at`이라는 비슷한 이름의 칼럼이 있는데, 이건 "내 앱"
  화면에 날짜를 보여주기 위한 복사본일 뿐 실제 만료와는 무관합니다. 그래서 이번 수정도 진짜
  `cloud_apps.expires_at`을 바꾸고, 화면용 복사본은 그 값을 그대로 따라가게만 만들었습니다.
- `expires_at` 칼럼은 이미 처음부터 있었기 때문에 **새 SQL을 실행할 필요가 없습니다.**

### 고친 것
- 앱을 Cloudflare로 배포할 때마다 서버에서 딱 한 번 호출되는 `/api/cloud-set-origin`이라는
  요청(배포 주소를 저장하는 용도)에 "만료일을 지금부터 30일 뒤로 늘린다"는 동작을 같이
  넣었습니다. 즉 **배포에 성공하는 순간 그 앱은 30일짜리로 바뀝니다.**
- 다시 배포하면 그때마다 또 "지금부터 30일"로 새로 계산됩니다 — 계속 쓰는 앱일수록 계속
  살아있는 구조라 자연스러운 동작이라고 판단했습니다.
- 안내 문구:
  - 저장 기능을 켜기 전 안내: "가입도 키 복사도 없이 한 번에 켜져요. 7일 동안 저장되고,
    배포한 앱은 30일 동안 저장돼요. 계속 쓰려면 요금제를 확인해주세요."
  - 저장 기능이 이미 켜진 상태의 안내는 "7일" 같은 고정 문구 대신, 실제 남은 날짜를 계산해서
    "OO일 뒤에 데이터가 정리돼요"로 보여주게 만들었습니다. 배포 전이면 7 근처, 방금 배포했으면
    30 근처의 숫자가 정확히 뜹니다.

## 작업 2. 배포된 앱의 "미리보기예요" 배지 수정

### 확인한 것
이 배지는 "저장 기능이 켜져 있는지" 하나만 보고 뜨는데, 그 상태는 "배포됐는지"와 다른
이야기입니다. **저장 기능을 아예 켜지 않고 배포한 앱**은 배포 후에도 계속 "지금은
미리보기예요. 배포하면 진짜로 저장돼요"라는 문구가 남아 있었습니다 — 이미 배포됐는데
"미리보기"라고 말하는 건 명백한 거짓말이라 이번 신뢰 수정 대상에 정확히 해당합니다.

### 고친 것
- 저장 기능이 켜진 앱: 배지 자체가 안 뜹니다 (기존과 동일하게 유지).
- 저장 기능 없이 도는 앱: "미리보기"라는 단어를 빼고 "데이터가 이 기기에만 저장돼요"로
  바꿨습니다. 배포 여부와 무관하게 뜨는 문구라 항상 성립합니다.
- 새로 만드는 앱부터 적용됩니다. **이미 만들어진 기존 앱들은 이 수정이 자동으로 적용되지
  않습니다** — 그 앱들의 코드는 이미 생성된 채로 저장돼 있어서, 다음에 그 앱을 다시 만들어
  달라고 요청해야 새 문구로 바뀝니다.

### 확인했지만 이번엔 안 고친 것 (지시 밖이라 보고만 드립니다)
"데이터가 이 기기에만 저장돼요"라는 문구가 엄밀히는 100% 정확하지 않을 수 있습니다. 저장
기능이 꺼진 상태에서 코랄레드 Cloud 방식(Track A)은 실제로는 브라우저 메모리에만 잠깐
담아두는 방식이라, **새로고침하면 데이터가 사라집니다** ("이 기기에" 계속 남는 게 아니라
"이 화면을 열어둔 동안만" 남는 것에 더 가깝습니다). 이번 지시는 "미리보기"라는 틀린 단어를
빼는 것이었고, 저장 방식 자체(메모리 → 기기 저장)를 바꾸는 건 지시 범위 밖이라 손대지
않았습니다. 필요하시면 별도 작업으로 진행하겠습니다.

## 작업 3. 배포 실패(미로그인) 시 로그인 버튼

### 확인한 것
"배포하기"는 로그인 여부와 상관없이 눌리고, 서버가 "로그인이 필요해요."라는 401 응답을
주면 그제서야 화면에 실패 알림으로 나타나는 구조였습니다. 그 알림에는 버튼이 "코랄레드에게
물어보기"(AI에게 이 오류를 고쳐달라고 요청) 하나뿐이었는데, 로그인 문제는 AI가 고칠 수
있는 게 아니라서 이 버튼은 의미가 없었습니다.
(참고: Netlify/Vercel의 "먼저 연결해주세요"는 이것과 다른 문제 — 코랄레드 로그인이 아니라
그 서비스 자체의 계정 연결이 안 된 것이라, 이번 수정 대상이 아닙니다.)

### 고친 것
- 배포 실패가 "로그인 안 됨"(401) 때문인 경우를 구분해서 표시하도록 했습니다.
- 이 경우 알림에 "코랄레드에게 물어보기" 대신 **"로그인하기" 버튼**이 뜨고, 누르면
  `/login`으로 이동합니다.

### 로그인 후 복귀 경로 (지시대로 버튼만 넣고, 여기 기록만 남깁니다)
현재 `/login` 페이지는 로그인에 성공하면 무조건 첫 화면(`/`)으로 이동합니다. 원래 하던
채팅으로 자동으로 돌아오는 기능은 없습니다. 만들려면 대략 이런 방식이 필요합니다:
1. "로그인하기" 버튼을 누르는 시점의 채팅 주소(`/chat/현재채팅id`)를 어딘가에 잠깐
   기억해둔다 (예: `/login?returnTo=...` 같은 주소 파라미터).
2. `login.tsx`가 로그인 성공 후 `/`로 고정하지 않고, 그 기억해둔 주소가 있으면 그쪽으로
   이동하게 바꾼다.

## 작업 4. 모바일에 저장 기능 버튼 추가

### 고친 것
모바일 헤더(`isMobileWorkspace`)에는 "배포하기" 버튼만 있고 저장 기능을 켜는 방법이
아예 없었습니다. 데스크톱과 똑같은 저장 기능 버튼 컴포넌트를, 라벨 없이 아이콘만 보이는
모드(`showLabel={false}`)로 배포하기 버튼 옆에 추가했습니다.

### 아이콘 버튼으로 선택한 이유
- 이 버튼 컴포넌트는 원래부터 "라벨 없이 아이콘만" 보여주는 옵션을 갖고 있어서, 새로 UI를
  만들 필요 없이 그대로 재사용할 수 있었습니다.
- "배포하기" 옆의 드롭다운(다른 방법으로 내보내기)에 넣는 방법도 검토했지만, 그 드롭다운은
  지금 개발자 모드에서만 보이게 꺼져 있고(`SHOW_DEV_TOOLS`), 성격도 "배포 방식 선택"이지
  "저장 기능 켜기"와는 다른 기능이라 억지로 합치면 오히려 헷갈릴 것 같았습니다.
- 결과적으로 헤더 폭을 거의 늘리지 않으면서(아이콘 버튼 하나 너비) 데스크톱과 동일한 기능을
  그대로 쓸 수 있는 방식을 골랐습니다.
